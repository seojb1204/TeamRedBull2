## 1. 결론

프로젝트에는 실제 LinUCB 학습, 튜토리얼 기반 초기 배정, 저장·복구, 비동기 DB 전송, 실제 C# 실험 도구, LIVE 진단까지 연결된 기반이 있다. 장기 포트폴리오로 발전시킬 기반은 충분하다.

우선 과제는 새 기능 추가보다 **검증 범위의 명확화, 자동 테스트의 CI 연결, 데이터 출처 관리, 재현 가능한 Windows 배포**다. “코드에 구현됨”과 “현재 main으로 실제 실행이 검증됨”을 구분해야 한다.

가장 설득력 있는 포트폴리오 주제는 **적응형 전투를 구현하고, 결정 근거를 관찰하며, 실제 코드로 재현·검증하는 도구까지 만든 프로젝트**다. 보스 수나 기능 수를 늘리는 것보다 이 연결을 증명하는 편이 효과적이다.

## 4. DDA-LinUCB의 실제 구현과 한계

### 4.1 구현 확인

- 난이도 행동은 `-2, -1, 0, +1, +2`의 5개다.
- 컨텍스트는 6차원이다: 상수, 패턴 성공률 관련 값, 전체 성공률 관련 값, 현재 레벨, 플레이어 파워, 재시도 관련 값.
- 행동별 행렬·벡터를 저장하고 관측 후 갱신한다.
- UCB 탐색 계수는 `0.18`이다.
- 행렬의 유한값·대칭성·양의 정부호 여부를 검사한다.
- 전투 시작 시 패턴별 난이도를 배정하고 종료 후 관측으로 학습한다.

**패턴마다 독립 LinUCB 모델이 있는 형태는 아니다.** `BossLearning`은 보스별 모델 하나를 가지고 패턴별 난이도·성공률·관측 기억을 관리한다. 정확한 설명은 “보스별 LinUCB 모델과 패턴별 상태를 활용한 난이도 배정”이다.

근거: [BossLearning·BanditModel](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Assets/Scripts/GameData.cs#L153).

### 4.2 실제 정책은 규칙과 LinUCB의 조합

| 조건 | 동작 |
|---|---|
| 3연패 이상 | 한 단계 하향 |
| 성공률 45% 미만 | 한 단계 하향 |
| 성공률 90% 초과 | 한 단계 상향 |
| 그 외 | 현재 난이도 주변 후보에 LinUCB·사전 점수·변화 비용 적용 |
| 성공률 60~80% | 최대 보상 |

따라서 “LinUCB 단독 제어”나 “성공률 60~80% 수렴 보장”으로 설명할 근거는 부족하다. 목표 구간을 선호하는 보상과 보호 규칙을 조합한 적응 시스템이다.

전투 종료 시 관측 수와 피격·패링·회피 합계의 정합성을 확인한다. DDA OFF·중도 포기는 학습에서 제외된다. 행렬 변화량, 배정 이유, 실제 후보 점수를 사용했는지 등을 진단한다.

근거: [전투 종료 학습·제외 조건](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Assets/Scripts/GameServices.cs#L97).

- 고정 난이도·규칙 기반·현재 DDA의 비교 효과

## 5. 튜토리얼 평가와 Cold Start

### 5.1 구현된 연결

1. 패링·회피·조작·시간을 관측한다.
2. 실습 시간과 설명·일시정지 시간을 구분한다.
3. 점수와 confidence로 `novice / normal / expert`를 분류한다.
4. 최초 평가와 재평가를 별도로 저장한다.
5. 개인 학습 기록이 없는 경우 초기 난이도에 활용한다.

평가 규칙 자체를 코드에서도 잠정 규칙으로 설명한다. confidence는 통계적으로 교정된 숙련도 확률이 아니라 관측 충족 정도를 반영한 휴리스틱이다.

튜토리얼은 별도 임시 `SaveData`로 실행한다. 완료 시 원래 프로필을 복제한 후보를 먼저 저장하며 재평가는 최초 평가 대신 별도 필드에 기록한다. 저장 실패 시 원본 진행을 유지하고 재시도를 제공한다. 튜토리얼 임시 기록을 일반 DDA 학습과 혼용하지 않도록 분리하는 코드와 관련 검사가 있다.

근거: [평가·시간 측정](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Assets/Scripts/TutorialSession.cs), [평가 저장·원본 복원](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Assets/Scripts/TowerGame.Tutorial.cs#L264).

### 5.2 초기 배정 우선순위

**개인 학습 → 조건을 충족한 숙련도 그룹 DB → 전체 DB → 유효 튜토리얼 → 중립**

유효 평가라도 confidence가 낮으면 튜토리얼 초기값은 중립이다. 충분한 근거가 있으면 초보 `-1`, 일반 `0`, 숙련 `+1`을 사용한다. 개인 기록은 보스 전투 기록 또는 패턴 관측이 있는지 판단한다. 공동 통계는 최소 관측 수 등의 조건을 만족해야 한다.

근거: [초기 배정·공동 통계](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Assets/Scripts/GameServices.cs#L139).

### 5.3 미구현 보장·남은 제약

- 첫 전투 전에 DB 응답이 도착한다는 보장은 없다.
- 공동 통계는 메모리 캐시이며 영속 캐시가 아니다.
- 통계가 늦게 와도 현재 전투의 배정을 소급 변경하지 않는다.
- 현재 수신 상태와 배정 당시 근거를 구분하는 진단은 있다.

이는 반드시 버그라는 의미는 아니다. 다만 동일 신규 프로필도 네트워크 도착 시점에 따라 첫 배정의 근거가 달라질 수 있으므로 실험에는 수신 시점을 기록해야 한다. 강제 대기·영속 캐시·새 재시도 정책은 별도 제품 판단 대상이다.

- 전송 OFF일 때도 로컬 보호 큐가 생성될 수 있다. **전송 비활성화와 수집·로컬 보관 비활성화는 다르다.**

장기 운영 전 보관 기간, 큐 용량, 내보내기·삭제 정책이 필요하다. 저장·개인정보 정책이므로 감독 에이전트가 임의 결정하면 안 된다.

| 숙련도 보호 RPC 전송·그룹 통계 수신 | 위 조건 + `proficiencySync: true` |
| 자동검증 실행 | 네트워크 차단 |
| `-towerDdaMonitor`만 사용 | 일반 플레이로 분류 |
| Lab DB 분석 | 별도 읽기 전용 집계 조회 |

`proficiencySync`는 생략하면 기본 false다. 이번 조사에서는 실제 설정 파일을 읽지 않았으므로 현재 실설정 값을 단정하지 않는다.

모니터 옵션의 자동검증 오인은 main에서 수정되어 있다. 정확히 `-towerDdaMonitor`를 예외로 하고 다른 `-tower…` 옵션은 자동검증으로 처리한다. 초기화 순서와 무관하게 네트워크 차단을 적용하도록 원시 프로세스 인자를 확인한다.

근거: [자동화 판별](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Assets/Scripts/AutoRun.cs#L31), [CloudSync 활성화 조건](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Assets/Scripts/CloudSync.cs#L44).

### 7.2 기존 전송과 보호 전송의 차이

기존 경로는 HTTP 409도 처리 완료로 본다. 숙련도 보호 RPC는 유효한 성공 응답을 확인한 후 큐를 승인한다. 화면의 DB 조회 성공과 게임의 INSERT 성공도 분리한다. 모의 HTTP 회귀 검사가 있지만 운영 송신 성공을 이번에 재확인한 것은 아니다.

### 7.3 안전 집계 API 구현

- 인자 없는 `exhibit_dda_summary_v1()`
- 고정 테이블·집계 범위, 동적 사용자 필터 없음
- 전용 비로그인·RLS 우회 없는 역할
- 공개 클라이언트에는 함수 실행 권한
- 원시 테이블 공개 SELECT를 열지 않음
- 신원·원시 JSON·키를 반환하지 않음
- 소표본 그룹은 null로 비공개
- 발표용·실제·다른 데모 출처 구분
- 실패 시 원시 조회나 관리자 키로 우회하지 않음

근거: [집계 SQL](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Docs/DB/migrations/20261121_exhibit_summary.sql), [Lab 집계 클라이언트](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Tools/DdaLab/database.py#L174), [배포·권한 안내](https://github.com/seojb1204/TeamRedBull2/blob/c56114ff97e463769b95f284c63604cda3c8eb6d/Docs/DB/EXHIBIT_SUMMARY_API.md).

최소 공개 조건으로 그룹 등에 3 owner, 패턴에 3 owner·20기회 등을 사용한다. 출처 전체 합계도 세 그룹 모두 공개 가능한 경우에만 반환한다. 비공개 셀을 0으로 취급하지 않는다. 집계 대상은 유효 최초 평가와 같은 출처로 올바르게 연결된 기록이며 원시 테이블 전체 건수와 반드시 일치하지는 않는다.

### 7.4 데이터 출처의 중요한 제약

발표용 판별은 `raw_json -> '_demo' ->> 'cohort' = 'demo_exhibit_20261121'`이다. `owner_key` 문자열 접두사로 판별하지 않는다. 패턴 샘플은 연결된 평가·전투의 소유자·프로필·전투 관계로 출처를 식별한다.

**Lab의 출처 분리와 게임의 초기 배정 출처 분리는 별개다.** Lab은 발표용·실제 기록을 구분하지만 게임의 그룹 Cold Start 수신은 여전히 `pattern_difficulty_by_proficiency` 뷰를 사용한다. 이 뷰에는 발표용 데이터가 섞일 수 있다.

장기 운영에서는 연구·전시 데이터가 실제 적응 근거에 포함되어도 되는지 먼저 정해야 한다. 이번 조사에서는 뷰나 게임 정책을 변경하지 않았다.

`_demo`는 출처 태그이며 진위 인증이 아니다. 최소 3소유자 기준도 차분 공격·시간차 추론까지 완전히 막는 개인정보 보호 보장은 아니다.

## 12. 감독형 개발 에이전트용 AGENTS.md 초안

다음은 제안문이다. 루트 AGENTS.md를 수정하지 않았다. 기존 팀원의 일상 PR 병합 권한을 변경하는 제안이 아니라 AI 에이전트의 실행 경계다.

```markdown
# 감독형 개발 에이전트 지침

## 기준
- CONTRIBUTING.md와 작업 범위에 적용되는 지침을 먼저 읽는다.
- 시작 시 branch, HEAD, 원격 main SHA, worktree, 미커밋 파일을 확인한다.
- 기존 사용자·팀원 변경을 수정하거나 폐기하지 않는다.
- 읽기 전용 요청에서는 파일·캐시·로그를 만드는 실행도 하지 않는다.

## 작업 범위
- 작업 목적, 허용 파일, 완료 조건, 제외 범위를 먼저 정리한다.
- 구현 전에 최신 main의 기존 기능과 의존성을 확인한다.
- 필요하지 않은 리팩터링·디자인·게임 정책 변경을 포함하지 않는다.
- 승인된 안전한 작업은 중간 확인 없이 완료한다.

## 승인 경계
- DDA 정책·보상·임계값·밸런스 변경은 명시적 승인이 필요하다.

- 운영 DB 접속·마이그레이션·쓰기·권한 변경은 별도 승인이 필요하다.
- 에이전트의 main 병합·Release 배포는 명시적 위임이 필요하다.
- 권한이 없으면 구체적인 수정안과 검증 근거까지 준비하고 중단한다.

## 데이터와 비밀값

- 발표용·실제·모의 데이터를 명시적으로 구분한다.

## 테스트
- 변경에 맞는 실제 코드 회귀 검사를 실행한다.
- 테스트를 삭제하거나 기대값을 약화하여 통과시키지 않는다.
- FAIL은 기존 문제·신규 회귀·환경 문제·검사 가정 문제로 분류한다.
- HEADLESS, Unity 컴파일, Windows 실행, 운영 연동 결과를 구분한다.
- 미실행·환경 차단은 PASS로 기록하지 않는다.
```

## 13. 개발 절차·테스트 규칙·GitHub 운영 제안

### 13.1 개발 절차

1. **작업 정의:** 문제·완료 조건·수정 범위·승인 경계를 확정한다.
2. **기준 확인:** 최신 main, 로컬 변경, 관련 기존 테스트를 확인한다.
3. **최소 구현:** 한 PR에서 한 가지 목적을 처리한다.
4. **영향 검증:** 변경 영역의 실제 코드 검사를 실행한다.
5. **자체 검토:** 데이터·정책·팀원 변경이 섞이지 않았는지 확인한다.
6. **Draft PR:** 실행 결과와 미검증을 함께 제출한다. 단, 개별 작업이 PR을 금지하면 생성하지 않는다.
7. **사람의 검토:** 정책·보안·저장·화면 판단을 받는다.
8. **통합 검증:** 병합 후 기준 SHA에서 필요한 재검사·빌드를 수행한다.

### 13.2 테스트 단계

| 단계 | 대상 | 권장 실행 시점 |
|---|---|---|
| 1 | 순수 로직·계약·오류 처리 | 관련 PR |
| 2 | 실제 C# HEADLESS·모의 HTTP·격리 PostgreSQL·Lab UI | 영향 영역 PR |
| 3 | Unity 컴파일·PlayMode·입력·화면 | 게임 코드·씬 변경 |
| 4 | Windows 클린 PC·패키지·LIVE·승인된 서버 연동 | 릴리스 후보 |

검증 기록에는 source SHA, 실행 명령, 환경 버전, 시드, 결과, 미검증 항목, 산출물 해시를 남긴다. 전체 파일 보존을 강제하는 과거 검사와 의도적인 기능 회귀 검사는 목적을 구분하되 실패를 무조건 무시하지 않는다.

### 13.3 브랜치·PR 규칙

- 최신 main 기반 목적별 브랜치와 작은 커밋을 사용한다.
- 직접 main push·force push·타인 브랜치 수정은 하지 않는다.
- 기존 팀원 권한과 브랜치 보호 규칙을 존중한다. AI가 스스로 main 병합을 결정하지 않는다.
- 핵심 회귀 검사를 필수 상태 검사로 연결하고 저장·DB 보안·DDA 정책 파일은 별도 리뷰 대상으로 지정할 것을 권장한다.
- 실제 보호 규칙 변경은 저장소 관리자의 승인이 필요하다.
- PR에는 문제, 최종 변경, 검증 결과, 미검증, 위험, 복구 방법을 적는다.
- 씬·Prefab·공통 파일은 수정 범위를 조율하며, 소스 전체 덮어쓰기로 충돌을 해결하지 않는다.
- 이 보고서 발행 작업은 사용자의 명시적 지시에 따라 문서 브랜치만 푸시하며 PR·main 병합·배포를 하지 않는다.

## 14. 승인 후 진행할 다음 작업

1. **문서·운영 규칙 PR:** AGENTS 초안 반영, 실제 빌드 진입점 수정, DB 배포 이력과 과거 검증 보고 구분.
2. **핵심 CI PR:** 기존 검사를 재사용해 DDA·저장·튜토리얼·HTTP·집계를 연결. 게임 정책 변경 없음.
3. **Windows 기준판 검증:** 기존 빌드·ZIP을 보존하고 현재 main 대응 여부, 무설치 실행, LIVE·DB·저장 복원을 확인.
4. **데이터 출처 정책 결정:** 발표용 데이터를 실제 Cold Start에 사용할지 결정. 결정 전 뷰·난이도 정책 변경 금지.

현재 확정할 수 있는 것은 기능과 검증 도구가 실제 코드로 존재한다는 점이다. 최신 main 전체 회귀 통과, 현재 운영 DB 상태, 최종 Windows 배포 품질은 별도 실행 검증이 필요하다. 위 후속 구현·검증은 이 문서 작성으로 수행되거나 승인된 것이 아니다.
